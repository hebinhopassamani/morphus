### 2. Nas Aplicações Criadas pelo Usuário (`/morphus/app/:appKey/...`) — Como funcionam as Rotas Filhas e qual Componente carrega?

Uma aplicação do usuário **não tem uma tela só** — ela tem quantas telas/páginas filhas o usuário cadastrar no banco!
Lembra que no Morphus **toda entidade tem uma `Key` única de 12 caracteres**?
- A **Aplicação** tem a `appKey` (ex.: `APP9821XKA12`);
- Cada **Módulo** tem a `moduleKey`;
- E cada **Tela / Submódulo** (`mpx_application_sub_modules`) tem a sua própria **`subModuleKey`** (ou `slug`, ex.: `PAG102938475` / `lancamento-horas`)!

Então, dentro de `/morphus/app/:appKey`, nós configuramos **rotas filhas dinâmicas**:

```typescript
{
  path: 'app/:appKey',
  component: UserAppShellComponent, // 1. Carrega a aplicação pela appKey e monta o menu lateral dela
  children: [
    {
      path: '',
      component: UserAppDefaultRedirectComponent, // Redireciona para a 1ª tela (Default) da aplicação
    },
    {
      path: ':pageKey',
      component: UserPageRendererComponent, // 2. Carrega a tela filha específica (ex: listagem/dashboard)
    },
    {
      path: ':pageKey/new',
      component: UserPageRendererComponent, // 3. Tela filha em modo criação (se usar sub-rota /new)
    },
    {
      path: ':pageKey/:recordId',
      component: UserPageRendererComponent, // 4. Tela filha passando o ID de um registro para edição/detalhe!
    },
  ],
}
```

#### O que acontece quando a URL muda para `/morphus/app/APP9821/PAG1029` e depois para `/morphus/app/APP9821/PAG5544/89`?
1. O menu lateral daquela aplicação (vindo de `mpx_menus` / `mpx_application_sub_modules`) tem um link diferente para cada tela criada pelo usuário:
   - Item 1 do menu -> `/morphus/app/APP9821/PAG1029`
   - Item 2 do menu -> `/morphus/app/APP9821/PAG5544`
2. O componente **`UserPageRendererComponent`** escuta a mudança do `:pageKey` (e do `:recordId` opcional) na URL:
   - Quando `:pageKey = PAG1029`, ele busca no banco o `HtmlContent`, `CssContent` e `JsContent` da tela **`PAG1029`** e renderiza ela;
   - Se dentro do HTML da tela `PAG1029` o usuário clicar em "Editar Cliente #89", o JS dele chama `Morphus.navigate('PAG5544', { recordId: '89' })`, a URL do navegador muda para **`/morphus/app/APP9821/PAG5544/89`**, e o `UserPageRendererComponent` troca para o HTML/CSS/JS da tela **`PAG5544`**, já entregando `Morphus.params.recordId === '89'` para o script dele carregar os dados!

### E como funciona a liberdade total de Layouts nessa 4ª Aplicação?

Quando o usuário entra em `/app/FINANCEIRO-KEY/dashboard`, quem recebe a rota na raiz **não é mais o `MorphusWorkspaceLayout` fixo**, e sim o **`MorphusAppEngineComponent`** (a casca camaleão da 4ª aplicação).

Ele olha para a aplicação (ou para a página) que veio do banco e decide na hora como envelopar a tela em **2 modalidades**:

#### Modalidade 1: Layouts Nativos Prontos do Morphus (`layoutKey` no banco)
O usuário escolhe num dropdown lá no construtor da aplicação qual estrutura ele quer:
- **`sidebar-default`**: Menu lateral retrátil + Topbar padrão (estilo ERP / Morphus Financeiro).
- **`topbar-modern`**: Sem barra lateral, menu horizontal no topo + área central larga (estilo Portal / CRM).
- **`minimal-clean`**: Sem menu lateral, apenas uma barra fina superior com botão de voltar ao Portal e perfil (perfeito para PDV, Kanbans de tela cheia, formulários focados).
- **`canvas-full`**: Tela 100% livre (o próprio HTML da página domina a tela inteira).

#### Modalidade 2: O Usuário Criar os Próprios Layouts dele no Banco (`mpx_application_layouts`)!
Mais insano ainda: o usuário pode criar um **Layout HTML próprio** e colocar duas marcações simples nele:
- `{{MORPHUS_MENU}}` -> Onde o motor injeta automaticamente os links dos Módulos/Submódulos da aplicação dele;
- `{{MORPHUS_CONTENT}}` -> Onde o motor injeta o HTML sanitizado da página atual (`dashboard`, `notas-fiscais`, `contas-a-pagar`)!

### Como funciona o Financeiro Real de uma Empresa em 4 Passos:

#### 1. A Entrada da Nota Fiscal (`Entrada de Notas Fiscais -> Importação de XML`)
Na vida real, ninguém quer digitar 50 campos de uma Nota Fiscal na mão. O fornecedor manda o arquivo **`.xml` da NF-e** (ou a Chave de Acesso de 44 dígitos da SEFAZ):
- Dentro do XML da Nota Fiscal já vêm prontos:
  1. **Emitente (Fornecedor)**: CNPJ, Razão Social, Nome Fantasia (`<emit>`);
  2. **Dados da Nota**: Número, Série, Data de Emissão, Chave de 44 dígitos (`<ide>`);
  3. **Itens / Serviços e Impostos**: Produtos, CFOP, ICMS, IPI, PIS, COFINS ou Retenções de Serviço (`ISS`, `IRRF`, `CSRF 4,65%`, `INSS`);
  4. **O Ouro (`<cobr><dup>` — As Duplicatas/Parcelas!)**: O próprio XML já traz quantas parcelas são, a data de vencimento de cada boleto e o valor de cada parcela!

#### 2. A Classificação (`Natureza de Operação / Centro de Custo`)
Quando a nota entra, o financeiro só responde **2 perguntas gerenciais**:
- **"O que é esse gasto?" (Plano de Contas / Natureza)**: Ex: *Software / Servidores*, *Material de Escritório*, *Energia Elétrica*, *Matéria-Prima*.
- **"De qual departamento/unidade saiu esse gasto?" (Centro de Custo / Filial)**: Ex: *TI*, *Comercial*, *Administrativo*.

#### 3. A Geração Automática no Contas a Pagar (`Títulos e Parcelas`)
Assim que a Nota Fiscal é conferida/aprovada, ela **gera automaticamente os Títulos (Parcelas) no Contas a Pagar**:
- Se a Nota Fiscal era de `R$ 3.000,00` em `3x` (30/60/90 dias), nascem **3 Títulos** no Contas a Pagar (`Parcela 1/3`, `2/3`, `3/3`) vinculados àquela Nota Fiscal, com status **`Aberto / A Vencer`** (ou **`Aguardando Aprovação`** se passar da alçada).

#### 4. A Baixa / Liquidação (`Baixas, Juros e Multas`)
No dia de pagar o boleto ou PIX:
- O financeiro dá a **Baixa do Título**: informa de qual **Conta Bancária** saiu o dinheiro, a **Data do Pagamento**, se teve **Juros / Multa** (por atraso) ou **Desconto** (por antecipação), e anexa o comprovante. O título muda para **`Pago / Liquidado`**!

# 🐳 O que é o Docker Compose e como ele funciona?

### A Analogia da Cozinha (Do Bolo ao Jantar Completo)
* **Dockerfile (A Receita de um Prato):** Como vimos antes, o `Dockerfile` é a receita passo a passo para preparar **um único prato** (por exemplo, só o bolo do Frontend ou só o assado do Backend).
* **Container (O Prato Pronto):** É o prato já assado e servido na mesa, rodando isolado.
* **Docker Compose (O Chef / Cardápio do Jantar Completo):** Um sistema real não vive de um prato só — ele precisa do **Frontend + Servidor Web (Caddy)**, da **API (.NET)** e do **Banco de Dados (PostgreSQL)** trabalhando juntos na mesma mesa. O **Docker Compose** (através do arquivo [docker-compose.yml](file:///c:/Projetos/morphus/docker-compose.yml)) é o **maestro da cozinha**: em um único arquivo você define todos os pratos do jantar, em que ordem eles devem ficar prontos, como conversam entre si e onde guardam os ingredientes.

---

### ⚙️ Como o Docker Compose funciona na prática (no Morphus)?

Quando você roda o Docker Compose, ele lê o arquivo [docker-compose.yml](file:///c:/Projetos/morphus/docker-compose.yml) e faz 4 coisas automaticamente:

1. **Sobe os Serviços (`services`) na ordem certa (`depends_on`):**
   * **`db` (PostgreSQL 18):** Sobe primeiro e faz um teste de saúde (`healthcheck` com `pg_isready`) para avisar quando está pronto para receber conexões.
   * **`api` (.NET Backend):** Espera o banco ficar saudável (`service_healthy`), lê o `Dockerfile` da pasta `mpx-backend` e sobe a API na porta interna `8080`.
   * **`caddy` (Frontend Angular + Servidor Web/HTTPS):** Lê o `Dockerfile` da pasta `mpx-frontend`, compila o Angular e sobe o servidor Caddy nas portas `80` e `443`, redirecionando chamadas `/api` para o container da API.
2. **Cria uma Rede Interna Invisível:**
   * Todos os containers entram na mesma rede privada. Assim, a `api` não precisa de IP fixo para achar o banco: ela simplesmente chama `Host=db;Port=5432` pelo nome do serviço!
3. **Injeta Variáveis de Ambiente (`environment` / `.env`):**
   * Lê senhas, nome do banco (`POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`) e domínio (`DOMAIN`) do arquivo `.env`, sem deixar dados sensíveis chumbados no código.
4. **Garante a Persistência dos Dados (`volumes`):**
   * Como containers são descartáveis, o Compose cria volumes permanentes (`postgres_data`, `caddy_data`, `caddy_config`) no disco da máquina. Mesmo que você destrua ou atualize os containers, os dados do banco e os certificados SSL continuam intactos.

---

### 💻 Comandos para Execução

Execute os comandos abaixo no terminal, na raiz do projeto (onde está o arquivo [docker-compose.yml](file:///c:/Projetos/morphus/docker-compose.yml)):

```bash
# 1. Subir todo o ambiente (compila as imagens se necessário e roda em segundo plano -d)
docker compose up -d --build

# 2. Subir apenas o banco de dados (muito útil para programar local rodando API e Front fora do Docker)
docker compose up -d db

# 3. Ver o status dos containers que estão rodando
docker compose ps

# 4. Acompanhar os logs em tempo real (todos os serviços ou apenas um, ex: api)
docker compose logs -f
docker compose logs -f api

# 5. Parar todos os containers (sem apagar os volumes/dados do banco)
docker compose down

# 6. Parar tudo e APAGAR os volumes (⚠️ zera o banco de dados do container)
docker compose down -v
```

## 🤖 Rafa

Cara, essa técnica que você usou aí:
```ts
export class User extends Morphus<IUser> {}
export interface User extends IUser {}
```
Isso em TypeScript se chama **Declaration Merging** (fusão de declaração de classe + interface com o mesmo nome), e é uma sacada de mestre! Porque quando você faz `new User(iUserVindoDoBanco)` e dá um `Object.assign` lá dentro da `Morphus<T>`, o TypeScript enxerga **todos os campos da interface `IUser`** diretamente na instância da classe `User` com autocomplete completo, além de todos os métodos utilitários da `Morphus<T>` (`deepClone()`, getters/setters, validações, etc.).

E sobre **não mandar a instância da classe direto pra API**: não é mito da sua cabeça não, você está **100% certo**!
Quando você trabalha com a classe na tela, ela carrega propriedades de controle de UI (como `isLoading1`, `isLoading2`, referências auxiliares, métodos do prototype). Na hora de mandar no `POST`/`PUT` para o backend C#, extrair somente a interface limpa (o JSON puro do contrato) evita trafegar lixo de UI na rede e evita erro de desserialização no backend!

### 2. O Combobox de Cores (`Theme`: Violet, Indigo, Crimson, Jade...) e o Menu de Usuário

### ✅ Questão 1
**Pergunta:** *A developer is building a Negotiation Agent that needs to iteratively refine an offer until both parties agree or a maximum of 5 rounds is reached. Which ADK Workflow Agent is specifically designed for this iterative refinement?*

👉 **Resposta correta:** **`Loop-Agent`** (4ª opção)

- **Por quê (para o Evernote):** No ADK (*Agent Development Kit*), os *Workflow Agents* controlam o fluxo de execução dos subagentes:
  - **`Loop-Agent`**: Executa subagentes repetidamente em um laço (*loop*) iterativo até que uma condição de parada seja atingida ou um número máximo de iterações (`max_iterations`, como as 5 rodadas) seja alcançado.
  - **`Sequential-Agent`**: Executa em sequência fixa (passo 1 -> passo 2 -> passo 3).
  - **`Parallel-Agent`**: Executa vários subagentes ao mesmo tempo em paralelo.

📌 **Resumo Completo para o Evernote — `Session state versus Memory Bank`**

### 1. O Problema: `The memory gap` (A lacuna de memória)
Mesmo com `VertexAiSessionService`, o **Session State** tem escopo restrito a **uma única conversa (`conversation-scoped`)**:
```text
# Session 1 (Monday):
User: "I prefer email notifications over SMS"
Agent: "Noted!"

# Session 2 (Friday - different conversation / novo session_id):
User: "How should I be notified?"
Agent: "I don't remember" # Porque o Session state pertence apenas à Session 1!
```

### 2. A Diferença Fundamental (Cai no Quiz!)
| Característica | `Session State` (`VertexAiSessionService`) | `Memory Bank` (`VertexAiMemoryBankService`) |
| :--- | :--- | :--- |
| **Escopo** | **Single session / conversation-scoped** (Apenas na conversa atual) | **Cross-session / user-scoped** (Entre todas as conversas do mesmo `user_id`) |
| **O que guarda?** | Histórico exato das mensagens e variáveis daquela conversa específica | Fatos extraídos, preferências do usuário e contexto de longo prazo |
| **Como funciona?** | Salva cada turno (`Event`) da sessão | Usa LLM nos bastidores para extrair fatos importantes da sessão (`add_session_to_memory`) e busca por semântica (`PreloadMemoryTool` / `LoadMemoryTool`) em novas sessões |
